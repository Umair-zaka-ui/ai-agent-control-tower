## A. Executive verdict

The V2 lab now runs entirely inside an egress-deny boundary enforced outside ACT: a Docker
`internal: true` network on Docker Desktop's Linux VM, no published ports, ACT's source mounted
read-only with its `.env` and `.keys` masked. All six boundary proofs passed from a stock Alpine probe
with no ACT code, and passed identically with the ACT container stopped. The lab rebuilt unattended
twice inside the wrapper (26–29 s bring-up) with a fresh key identity each time, and the full V2
baseline reproduced every behaviour — GOVERNED refused 6/6, containment REFUSED with revocation
effective, zero unexpected canary appearances, positive control firing — with only latency improving.
No ACT code changed; nothing adversarial ran. The verdict is **CONDITIONAL** on one honest limit the
brief anticipated: this wrapper is a shared-kernel container boundary, adequate for V3's injection,
MCP, identity and boundary-abuse scenarios, but **not** for T12 code-execution / sandbox-escape
scenarios, which need their own VM-based environment.

## C. Mechanism chosen and why

An `internal: true` Docker network containing every lab component, chosen as the strongest boundary
this host genuinely supports: it is the Linux-namespace option as Docker Desktop exposes it (no default
route, no NAT, no upstream DNS), enforced by the Docker VM's netfilter rather than by anything ACT does.
Rejected: a disposable VM (not provisionable unattended from committed artifacts on this host without
new tooling; recommended for T12), and loopback-only binding (the V2 state, insufficient).

## D. Properties table

Egress default DENY (on-link route only) · allowed destinations = the lab's own containers only ·
independence = Docker/VM netfilter, proven with a foreign probe and with ACT stopped · host protection =
`host.docker.internal` unresolvable and the host LAN IP unreachable while the dev API and dev Postgres
were live · production separation = read-only source mount, `/app/.keys` empty tmpfs, `/app/.env`
empty file, image built from `requirements.txt` only, dev DB unreachable · disposability = `wrap_down.py`
asserts no container/network/volume and deletes keys and run dir · reproducibility = `wrap_up.py`
unattended from committed files. Details and evidence pointers in `ISOLATION_WRAPPER.md`.

## E. Boundary proofs

All six passed (`BOUNDARY_PROOF.md`): external names SERVFAIL at Docker's embedded resolver and
external IPs have no route; host services unreachable by name and by LAN IP; `169.254.169.254` "Network
unreachable" while the lab's metadata decoy answers; attacker-sim, canary targets, MCP zone, registry and
DB reachable; identical with ACT stopped; DNS for external names blocked at the resolver (not
permitted-but-unroutable). Independence was achieved by using a stock `alpine:3.20` probe with no ACT
code and by re-running every proof with the ACT container stopped.

## I. Divergences from the V2 baseline

## J. Wrapper limits + T12 recommendation

Shared-kernel containers (escapes land in the Docker VM); host-initiated channels (exec, bind mounts)
are outside the boundary — an evidence-hash ledger is a V3 prerequisite; side channels unmitigated;
DNS-shaped traffic to lab-owned names remains a residual for V3 to test; the attacker-sim and decoys
are reachable by design; a compose edit could silently re-open egress, so `wrap_up.py` re-asserts
`internal=true` and no published ports every build. **T12 recommendation: not safe in this wrapper;
give T12 its own disposable VM with a host-only network.** Full text in `WRAPPER_LIMITS.md`.
