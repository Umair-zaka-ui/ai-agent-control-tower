# O11_CONFIRMATION — the image-embeds-key-material gap still stands (informational, §9)

**Verified on this tree (`validation/v9-scale`, off `224aea8`; `main` at `9667707` carries the same files).**
No image was built and nothing was modified — this is a structural confirmation, recorded so the item is
not lost before V10. Raw: [`evidence/v9_o11.json`](evidence/v9_o11.json).

| fact | value |
|---|---|
| compose build context | `docker-compose.yml`: `build: ./backend` |
| Dockerfile | `backend/Dockerfile`: `COPY . .` (whole context) at line 20 |
| `.dockerignore` | `backend/.dockerignore` exists; patterns: `.venv/ venv/ __pycache__/ *.pyc .pytest_cache/ .mypy_cache/ .ruff_cache/ .env .git/ tests/` — **no `.keys/` entry** |
| `backend/.keys/` on disk | **exists**: `model_credentials.key` (the encryption key), `default.v1/v2/v3.pem` (**private** signing keys) + their `.pub.pem`, `does-not-exist.v1/v2.pem` |
| git | `.gitignore` excludes `.keys/`, `backend/.keys/`, `lab/.keys/` — the material never reaches the repository, only the build context |

**Conclusion: O-11 stands.** A `docker compose build` on this tree copies the live encryption key and every
private signing key into the image layer. It remains a **mandatory pilot blocker** (master plan §Z,
"unprotected credential leakage") and **must close before V10 goes near a real organization's environment,
even OBSERVE_ONLY** — a control plane that ships its own key material cannot be placed in a customer context.

## What V9 found on top of it (new, V9-4)

`backend/.keys/` holds **92,694 `test-*.pem` files (~126 MB)** — signing keys generated by the test suite,
one pair per test-created signing key, never cleaned up (the suite's key directory defaults to the same
`./.keys/` as the dev install). Two consequences:

1. the O-11 image would embed not only the dev keys but ~126 MB of test key material;
2. the key directory is a W-6-style accumulation: 11 real files are buried under 92k residue files, which
   makes any manual key-hygiene check (the `keys backup` archive copies **every** `*.pem` it finds) noisy
   and slow, and makes the recovery archive itself carry thousands of irrelevant private keys.

## Recommendation (not V9 work)

A bounded O-11 fix between V9 and V10, in the shape of the M4.11 integrity work:
- `backend/.dockerignore`: add `.keys/` (and consider `.env*`, `*.pem`, `*.key` as belt-and-braces);
- a build-time guard test that asserts the build context excludes key material (the `test_ac01`-style
  file-reading guard the repository already uses for tracking files);
- the test suite's signing-key fixtures should use a per-session temporary key directory
  (`SIGNING_KEY_PATH` override) so residue never lands in `backend/.keys/`; a one-off cleanup of the
  92,694 residue files after that lands;
- `create_key_material_archive` should copy only the configured key id(s), not `glob("*.pem")`.
